# 实际聊天选区迟迟无消息

用户反馈：资源早已下载，左侧不断显示识别，右侧等很久才有消息。

## 根因与复现

读取正在录制页面（未暂停或刷新用户录制）：实际选区为 516×126，最近一次推理约 101 毫秒，但首条消息约在会话开始后 52 秒才出现。

从用户本地已保存的首段视频抽取 0/10/30/50 秒四帧，只在本机测试，不上传、不提交。旧 splitLines 的完整行数量为 0/0/1/0；唯一的一行高度约 64px。透明聊天背景的纹理参与对比掩码，绝对阈值和闭运算将多行连接成大块，再被边缘截断规则过滤。推理耗时短并不代表所有文字已经读到。

## 修复

- 行投影只使用高对比且最大 RGB 通道不低于 175 的亮字核心；识别输入仍保留原始 RGB 裁剪。针对 QQ 三国亮字聊天，不声称支持所有暗字文档。
- 只对首末物理行做边缘严格检查，不再对小窗口前后三行全部严审；贴顶、贴底和异常残行仍过滤。
- 返回检测行/丢弃行诊断及逐行推理进度。页面显示 GPU/CPU、识别行数、新增/修订消息和空结果原因，不再只显示一个耗时。
- 没有修改人名、频道或合并规则；已知不完整频道仍可能无法整理为消息，不能将它误报为 GPU 故障。

## 实际验证

同四帧修复后完整行数为 5/5/5/3。实际浏览器 WebGPU 推理分别约 1129/493/510/333 毫秒；首帧即整理出 3 条消息，后续帧正确更新或新增，顶底残行仍被排除。模型缓存初始化约 3.8 秒，此处未包括首次网络下载。

独立复验 68/68 测试与类型检查通过，新增暗纹理背景上的黄/白/绿/粉/青文字、首末残行、小框完整首末行回归；Review 确认修复不含人物或具体视频硬编码，允许发布。低亮度文字或更亮背景仍可能影响分行；对比投影阈值并非通用文档 OCR 承诺。

原始样本保留于本机 .tools/ocr-delay，不进入 Git 或部署产物。回归和 Review 完成后发布为一个后续提交，不改写已推送历史。用户真实页面需停止并保存后刷新才会加载新代码。
