## 新需求如何落文档

1. 从 [SPC 模板](templates/SPC.md) 建立下一编号的需求规格，先写目标、非目标和可检查的验收项，再实施。编号独立于日期，不复用、不按每次讨论复制新规格。
2. 涉及模块边界、存储/协议、部署、依赖选型或重大取舍时，从 [ADR 模板](templates/ADR.md) 建立独立决策记录，关联对应 SPC。
3. 一个 SPC 可关联零个或多个 ADR；普通缺陷修复无新决策时，在 SPC 明确“无新增 ADR，沿用 ADR-xxxx”，不创建空 ADR。
4. 实现时更新 SPC 的任务与证据；当前架构发生变化时更新架构文档。测试计划和结果可以按需另存并从 SPC 链接，不复制多份互相冲突的状态表。
5. 交付记录代码审查、测试、提交和部署版本；用户未明确验收时保留“待用户验收”。纯文档迭代没有部署需求时明确“不适用”。

SPC 的需求状态与交付状态分开：需求可为草案、已确认、实施中、待用户验收、已验收、取消；代码、测试、提交、部署各自记录证据。ADR 使用提议、已采纳、已拒绝、已取代；ADR 已采纳不代表功能已经交付或用户已经验收。

已采纳 ADR 的结论变更时新建 ADR，在旧记录注明被谁取代；可修正错字和链接，不覆盖历史理由。2026-11-24 补建的早期 SPC/ADR 均标注“事后整理”，不声称它们是在当时事前编写或完成正式评审的。
